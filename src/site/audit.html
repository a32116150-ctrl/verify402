Where a service charges
and delivers nothing.

A payment can settle and the response can still be lost. Not through a bug in USDC and not through the facilitator — through ordering: what is written down before the settle call, and what a retry is allowed to be answered with. I review one payment path end to end and name the windows that cost money.

The windows

Five ways it goes wrong.

Each one is a design decision, not a typo. That is why they survive code review and show up in production instead.

01

The record lands after the settle

The rail accepts the payment; the process dies before the record is durable. Now there is a charge and no evidence it ever happened.

02

The handler runs before confirmation

Work is done and the reply is lost. The payer paid, the effect may have happened, and nobody can find the response.

03

Two copies, one payment

Verification is read-only. Two concurrent retries both pass it, both run the handler, and only one settlement exists.

04

A retry gets a fresh 402

The caller signs again because the challenge looks like "not paid yet". One purchase becomes two.

05

The timer evicts a paid response

A staging timeout removes the only stored copy of a response the caller already paid for — the classic lost-reply case.

Scope

What I check.

01

Settlement ordering

Is there a durable attempt boundary written before the settle call? Is promotion gated on a confirmed settlement, or on a timer?

02

Response gating

Can any response be released or replayed without a confirmed settlement behind it?

03

Idempotency identity

Is a key bound to one operation by request fingerprint and verified payer scope — or keyed on output bytes, which two different operations can share?

04

Concurrency

Is there an atomic claim before the handler, or only a read-only verify? Read-only verify lets every concurrent copy run once.

05

Crash windows

Kill points at each durable write — claim, staging, stored response, settling, settle result, delivered, receipt — before and after each write, plus the span between an accepted settlement and its record.

06

Retry semantics

Does an in-flight retry get a different answer from an unresolvable one? Is a payment challenge ever returned to a caller whose payment might already have landed?

07

Expiry and void

Is void used only where non-settlement is proven, or as a way to make a stuck operation look finished?

08

The operator path

If it ends stuck: is the record retained, the key blocked, and a human alarmed — or does it fail silently?

Deliverable

A report you can act on.

For each finding: severity, the exact interleaving that produces it, the observable symptom, and a concrete fix. Every finding comes with a reproduction that does not depend on my code — a scenario you can turn into a test.

Then a call to walk through it. Implementing the fixes is a separate engagement, quoted before it starts.

What this is not

Not a smart-contract audit, not a penetration test, not a code-style review. I do not touch keys, wallets, or production data. I read and test the payment path you point me at.

Why me

This is the thing I actually work on.

I wrote the recovery extension currently under review at x402-foundation/x402#3848 — the rule for when a retry may be served for free, what must be durable before settlement, and how a retry is answered while the outcome is still unknown. Two independent engineers have reviewed it across two rounds.

Before that, the naive version of the same design was reproduced with two real defects in public: recovery before settlement, and promotion by response hash alone. Both are in the spec's history, with the reviewers named.

I also built a crash-conformance harness that kills a service at 29 points and compares the state that comes back out. Its results are published here — including the vectors where my own implementation diverges, and why. A review that only shows you its passes is not a review.

The service on this site is the reference implementation: Apache-2.0, testnet, no external customers. That last part is true and it is on every page.
