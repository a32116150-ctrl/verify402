Solana mainnet · USDC · x402

Solana x402 payments with verify402.

Every paid verify402 check can be paid in USDC on Solana mainnet, at the same price as on Base. Before an agent pays a Solana x402 request, anywhere, the free /preflight gate checks the request. And if a Solana payment's confirmation is lost on the way back, the outcome is settled from the chain, not guessed.

Check a Solana payment request See the paid checks

01 · Pay in Solana USDC

Two ways to pay, one price.

Each paid route answers with an HTTP 402 that offers two options: USDC on Base and USDC on Solana. Pick either; the price is the same, from $0.02 to $0.10 per call. Payments settle through the Coinbase CDP facilitator.

To pay on Solana, use an x402 client that can sign Solana payments. The verify402 MCP server pays on Base today. Always take the network, asset and price from the live 402 challenge: it is the authority, not this page.

02 · Free check before you pay

Check a Solana x402 request, field by field.

Pass the Solana payment request your agent received to POST /preflight. The gate checks the scheme, that the network is Solana mainnet, that the asset is the canonical USDC mint, the amount against your cap, the payee (a system or token program as payee is a BLOCK), the resource URL and host, and the timeout.

Request

POST /preflight
{
  "kind": "payment",
  "payment": {
    "scheme": "exact",
    "network": "solana:5eykt4UsFv8P8NJdTREpY1vzqKqZKvdp",
    "asset": "EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v",
    "amount": "20000",
    "payTo": "<payee from the 402>",
    "resource": "https://vex402.online/safety",
    "maxTimeoutSeconds": 60
  },
  "policy": { "maxAmountUsd": 0.05, "allowedResourceHosts": ["vex402.online"] }
}

Response (trimmed, from the live gate)

{
  "verdict": "PASS",
  "structural_only": true,
  "checked": ["scheme", "network", "asset", "amount", "payee", "resource_url", "resource_host", "timeout"],
  "structural_only_reasons": ["Solana payment preflight is structural: no slot binding and no balance check", …],
  "notChecked": ["solana slot binding", "payer_balance", "payment proof / signed payload", …],
  "receipt": { … }
}

On Solana, a PASS means the request is well-formed

The response says so itself with structural_only: true. On Solana the gate does not read the payer's balance, bind the answer to a slot, or check a signed payment. Those stay in notChecked on every answer.

03 · Payment recovery

A lost confirmation is settled from the chain.

Sometimes a payment goes through but the confirmation never makes it back, for example when a connection drops. On Solana there is no single “was this used?” call, so verify402 checks the chain two ways: it looks for the payer's own signature in the payer's recent transactions, and it checks whether the transaction's recent blockhash has expired, after which it can never land.

The chain showsWhat happens
The payment landedIt counts. Retry with the same idempotency key within 10 minutes and the answer is served without paying again.
The payment can no longer landNothing was charged. The request can be paid again.
Not sure yetThe key stays blocked until the chain gives a definite answer. It never guesses.

Legacy and versioned Solana transactions are read. The recovery design is written up in the payment review and the x402 recovery proposal.

04 · Honest limits

What verify402 does not do on Solana yet.

Solana support covers payments and token safety. The paid /safety check reads a Solana token's own controls: who can mint more, freeze holders, take tokens from any wallet, or charge a fee on every transfer. verify402 does not check Solana transactions such as swaps or token delegations, and it does not quote Solana swap prices. The transaction gate, with its plain-language advice and risk limit, reads 22 EVM networks, and the paid market checks measure 7 of them.
